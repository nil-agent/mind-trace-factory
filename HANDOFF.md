# HANDOFF — make the data factory runnable today

## Mission for this work session

The goal for the next few hours is **not** to redesign this project or train a model.

The goal is to make this repository capable of running an end-to-end synthetic-data generation loop:

1. obtain/create structured synthetic ground truth,
2. render the story with a generative LLM through an OpenAI-compatible API (OpenRouter for today's run),
3. verify the story against the structured source in both semantic directions with Jev,
4. generate a natural-language reasoning/thought trace one step at a time through OpenRouter,
5. use Jev to score candidate next thoughts and guide the stochastic search,
6. detect when enough reasoning has accumulated,
7. generate the final natural-language answer through OpenRouter,
8. verify the final answer proposition-by-proposition against the answer-key projection of the ground truth with Jev,
9. persist a complete audit trail,
10. after human inspection/approval, run the generator continuously to accumulate accepted examples.

By the end of today, the desired deliverable is **a reliable generator producing inspectable accepted/rejected examples**, not a LoRA, not an SFT exporter, and not a production service.

---

## Hard separation of responsibilities

There are two model backends and they have deliberately different jobs.

### OpenRouter / OpenAI-compatible generator

Use the OpenAI-compatible API for **all generative operations**:

- structured ground-truth generation once the fixed fixture works,
- structured-ground-truth -> natural story,
- natural story -> atomic claim extraction,
- candidate next-thought generation,
- final-answer generation,
- final-answer -> atomic claim extraction.

For today's implementation, OpenRouter is the provider. Keep the wrapper generic enough that another OpenAI-compatible base URL can be substituted later.

**Do not use Jev for text generation.**

### Jev / TypeSafe System One

Use Jev only for **judgment/scoring**:

- ground-truth proposition -> story entailment scores,
- story claim -> ground-truth support scores,
- candidate next-thought validity scores,
- ready-to-answer score,
- answer-key proposition -> final-answer entailment scores,
- final-answer claim -> answer-key compatibility scores.

**Do not ask Jev to write stories, thoughts, claims, or answers.**

## Official client integrations

### Jev: use the official TypeSafe Python SDK

Use the official package:

```bash
pip install typesafe-sdk
```

The official TypeSafe repository currently identifies the package as `typesafe-sdk`. The client reads `TYPESAFE_API_KEY` from the environment.

The intended integration shape is:

```python
from typesafe_sdk import Noul, TypeSafeClient

with TypeSafeClient(model=jev_model) as client:
    response = client.system_one(
        state=state,
        questions={
            "q1": Noul(
                instructions="...",
                criteria={
                    "true": "...",
                    "false": "...",
                },
            ),
            "q2": Noul(instructions="..."),
        },
    )

score = response.nouls["q1"].noul
```

Current official SDK details verified before this handoff:

- package: `typesafe-sdk`
- official repo currently reports version `0.7.2`
- API key environment variable: `TYPESAFE_API_KEY`
- default upstream model alias: `jev-latest`
- named Noul responses are exposed by `response.nouls[name].noul`
- `system_one` accepts a mapping of many named questions in one request
- it exposes model/usage metadata on the response
- SDK retry/error handling already exists; use it rather than writing raw HTTP unless there is a blocking SDK bug

Useful upstream references:

- <https://github.com/typesafe-ai/typesafe-sdk-python>
- <https://docs.typesafe.ai/sdk/python/>
- <https://docs.typesafe.ai/primitives/noul>

Implement our existing `JevClient` protocol with a thin `TypeSafeJevClient`. Keep the rest of the pipeline unaware of the official SDK types.

Suggested env:

```bash
TYPESAFE_API_KEY=...
JEV_MODEL=jev-latest
```

Do not commit keys.

## Ground truth semantics

For today's implementation, the structured ground truth is the authoritative synthetic source. It does not need to correspond to a real event.

The existing `Proposition` records are enough for the first generator.

Two projections matter:

### Story source

```python
story_source = [
    p for p in ground_truth.propositions
    if p.required_in_story
]
```

Only this projection is passed to the story writer.

The story writer must **not** receive answer-key propositions.

### Answer key

```python
answer_key = ground_truth.answer_key()
```

This is the semantic target for the final answer. It should include positive mental-state facts **and important uncertainty/negative constraints**, e.g.:

- "Maya's confidence in simple forgetfulness decreases."
- "Intentional exclusion becomes more plausible but is not established."
- "Maya does not know whether Priya influenced the outcome."

The answer-key projection is deliberately different from omniscient world truth. A world fact may be true while a character is not entitled to know it.

For the first live run, use the existing hand-written Maya fixture. Once the whole pipeline works, add OpenRouter generation of `GroundTruth` JSON conforming to this same schema. Treat generated structured ground truth as authoritative for that synthetic sample after schema validation.

Do not make automatic ground-truth generation the first blocker.

## Stage 1 — structured ground truth -> natural story

### Generation

Input to OpenRouter:

- only `story_source`
- instructions to produce a natural, coherent scenario
- no answer key
- no hidden verification commentary

The story should be a linguistic realization of the source, **not creative expansion**. Initially reject unsupported factual embellishment.

### Verification is proposition-level and bidirectional

This is important.

Do **not** collapse verification into:

- "does the story contain all the facts?"
- "is the story consistent?"

Instead use one Noul question **per proposition/claim**, batched into two Jev calls.

Let:

```text
G = story_source propositions
S = generated natural story
E(S) = atomic factual claims extracted from S
```

#### Jev call A: G -> S coverage

Create one Noul question for every `g_i in G`:

> Does the scenario clearly communicate proposition Gxx: "...", judging semantic meaning rather than wording?

Send all of those questions in **one Jev request**.

This yields independent scores with provenance:

```json
{
  "G01": 0.98,
  "G02": 0.94,
  "G03": 0.91
}
```

#### Claim extraction

Use OpenRouter to extract every independently truth-evaluable factual assertion from the story.

The extractor is a parser, not a verifier.

Require strict machine-readable JSON such as:

```json
{
  "claims": [
    {"id": "S001", "statement": "..."},
    {"id": "S002", "statement": "..."}
  ]
}
```

Extraction requirements:

- preserve who did what,
- preserve who observed/heard/was told what,
- preserve temporal relations,
- preserve explicitly stated goals/preferences/relationships,
- preserve explicit negations,
- do not infer unstated facts,
- split compound claims when they can be independently true or false.

#### Jev call B: E(S) -> G soundness

For every extracted claim `s_j`, ask independently:

> Is this claim fully licensed by the story-source ground truth?

Treat both contradictions and unsupported factual additions as failures.

Again: one Jev request containing one Noul question per extracted claim.

**Use `story_source`, not the complete ground truth, as the reverse verifier state.**

That is a correction to the current scaffold.

### Initial acceptance policy

Make these configurable, but start with:

```text
min forward proposition score >= 0.85
min reverse claim score       >= 0.85
```

Do not use only averages. One badly missing/unsupported proposition should fail the scenario.

On failure:

- save the failed attempt and all scores,
- regenerate from the same structured source,
- at most 3 attempts initially,
- optionally include the failed proposition IDs/claims as concise corrective feedback in the next story-writer prompt.

Do not silently mutate the structured ground truth to make the story pass.

## Stage 2 — thought-search loop

The generator side and the critic side intentionally see different information.

### Candidate generator sees

- natural scenario,
- target character/person,
- thought trace so far.

It must **not** see the answer key or structured hidden ground truth.

This separation is essential. Jev is allowed to see ground truth; the text generator is not.

### Candidate format

At each step ask OpenRouter for `N` independent plausible next-thought continuations.

Initial default:

```text
N = 8
```

Return strict JSON:

```json
{
  "candidates": [
    "...",
    "...",
    "..."
  ]
}
```

Each candidate should be:

- one short natural cognitive continuation,
- not an explanation of why it is plausible,
- not a final answer,
- allowed to be a hypothesis/question/speculation,
- consistent with the target character's perspective,
- diverse from the other candidates.

Deduplicate exact/near-exact candidates before scoring if easy; do not spend hours on semantic deduplication today.

### Jev candidate scoring

Use one Noul per candidate, all in one Jev request.

State should contain:

- full structured ground truth relevant to this synthetic instance,
- natural scenario,
- target character,
- complete trace so far,
- candidate map keyed by stable candidate IDs.

Question semantics:

> Is this a reasonable thought for this character to entertain at this point?

"Reasonable to entertain" is intentionally more permissive than "is this belief correct."

A thought may:

- introduce a hypothesis,
- express uncertainty,
- consider a wrong hypothesis,
- later be rejected.

Reject or score down thoughts that:

- assert inaccessible information as known,
- contradict established information without a reason,
- jump to unjustified certainty,
- are psychologically/epistemically incoherent with the trace so far.

### Selection policy

For the first implementation preserve the policy we discussed:

1. sort by Jev score descending,
2. cut the low-scoring tail,
3. keep the top fraction,
4. shuffle the survivors,
5. select the first survivor,
6. append it,
7. rescore from the new trace on the next iteration.

Initial:

```text
keep_fraction = 0.5
```

So with 8 candidates, keep the top 4, shuffle those 4, choose uniformly.

Do **not** concatenate several candidates scored against the old trace. Every append changes the state; generate/score again after each chosen thought.

Do **not** take the argmax by default. Diversity is a feature.

Persist every candidate, score, cut decision, shuffle/selection, and resulting trace.

### When to stop

Do not try to detect a final-answer sentence inside the thought stream.

After each appended thought, once `min_steps` is reached, issue a separate Jev Noul:

> Has the trace developed enough relevant reasoning to support a correct, appropriately uncertain final answer? Return true when further thought is unlikely to materially improve the answer.

Initial configuration:

```text
min_steps = 3
max_steps = 12
ready_threshold = 0.85
```

Stop when:

```text
steps >= min_steps AND ready_score >= ready_threshold
```

Force stop at `max_steps`.

Persist every readiness score.

These numbers are experimental defaults, not conclusions. Do not tune them extensively before the human checkpoint.

## Stage 3 — final answer

Once the stop condition fires, switch modes explicitly.

Do not ask the thought generator to spontaneously emit a "final answer."

Use a separate OpenRouter final-answer prompt.

Input:

- natural scenario,
- target character/person (for the initial single-target pipeline),
- complete generated thought trace.

Do not pass structured ground truth or answer key.

Prompt intent:

- answer the actual Theory-of-Mind question,
- summarize the character's resulting mental state,
- preserve uncertainty,
- do not claim hypotheses as facts unless warranted,
- do not mention the scoring/search machinery.

The trace may have explored and rejected wrong ideas. The final answer should reflect the resolved state, not repeat every speculative thought.

## Stage 4 — final-answer semantic round trip

Yes: use the same retraction/section-style idea here.

Let:

```text
K = answer-key proposition set
A = generated final answer
E(A) = atomic claims extracted from A
```

Again use **sets of proposition-level questions**, not two aggregate judgments.

### Jev call C: K -> A coverage

For each answer-key proposition `k_i`, ask:

> Does the final answer communicate this answer-key proposition with the appropriate certainty?

All questions batched into one Jev call.

### Extract answer claims

Use OpenRouter to atomize the final answer.

For final-answer extraction, prefer mental-state propositions such as:

- "Maya suspects deliberate exclusion more than before."
- "Maya is not certain the exclusion was deliberate."
- "Maya lacks evidence that Priya caused it."

Do not let the extractor turn hedged language into certain claims.

### Jev call D: E(A) -> K soundness

For every extracted final-answer claim, ask whether it is compatible with the answer key, including:

- information-access constraints,
- uncertainty,
- belief strength/direction,
- explicit unknowns,
- goal/emotion statements present in the key.

A true omniscient-world fact is **not** automatically valid if the final answer improperly attributes that fact as knowledge/belief to the character.

The answer verifier therefore judges the character-level answer key, not raw world factuality.

Initial acceptance policy:

```text
min answer-key -> answer score >= 0.85
min answer claim -> answer-key score >= 0.85
```

Make configurable.

On failure:

- save the rejected answer and all verifier details,
- retry final-answer generation from the same scenario + trace up to a small bounded count (e.g. 2-3),
- do not rewrite the trace merely to make an answer pass unless later experiments justify it.

## Error handling

Keep this boring.

### Jev

Use the official SDK and catch its public errors where useful.

Authentication failure should abort clearly.

Transient/rate-limit/timeout errors may use the SDK retry policy. Do not implement unbounded retry loops.

### OpenRouter / generator API

Use bounded retries for network/rate-limit/server errors.

For malformed structured generation:

- save the raw output,
- retry a small number of times with a concise "valid JSON only" correction,
- then mark the stage/run failed.

Never swallow an exception and emit an apparently accepted record.

## Acceptance and output

A run is accepted only if:

1. structured ground truth is valid,
2. scenario passes every forward and reverse gate,
3. thought search reaches a stop condition or max step without runtime failure,
4. final answer is generated,
5. final answer passes every forward and reverse gate.

Persist rejected runs too; they are useful debugging data and may later become preference/reward-model negatives.

For end-of-day batch output, a simple append-only JSONL is enough, e.g.:

```text
out/accepted.jsonl
out/rejected.jsonl
```

Each accepted row should contain or reference:

- scenario,
- explicit natural-language thought trace,
- final answer,
- run ID,
- target person,
- verification summary,
- generator/Jev model metadata,
- seed.

Full ground truth and raw receipts can remain in the run directory.

## Two principles not to accidentally violate

### 1. The generator must not see the answer key during reasoning/final-answer generation

Otherwise we manufacture apparent reasoning by leaking the target.

The critic/verifier may see structured truth.

The generator should reason only from the natural scenario and its own trace.

### 2. Verification is not one global "looks good" score

Our retraction/section-inspired test is element-wise.

For the story:

```text
for every source proposition g:
    story semantically entails g

for every extracted story claim s:
    story_source licenses s
```

For the answer:

```text
for every answer-key proposition k:
    final answer semantically entails k with correct certainty

for every extracted answer claim a:
    answer key licenses a with correct epistemic status
```

The questions can and should be batched into one Jev API request per direction, but each proposition keeps its own score and identity.

That provenance is central to the experiment.
